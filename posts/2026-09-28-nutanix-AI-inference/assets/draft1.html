How an inference request behaves

Training is a long, throughput-oriented batch job that changes model parameters. Inference holds those parameters fixed and answers requests online. The path is layered: an application calls an API gateway; the gateway routes to a serving framework such as vLLM or TensorRT-LLM; the framework drives model execution; and the runtime finally schedules work onto GPU hardware. The serving-framework layer is where our team will operate the service, but every layer beneath it can set the latency ceiling.

PREFILL

The prompt is processed largely in parallel to build attention state. This phase is rich in matrix work and is usually compute-bound.

DECODE

The model emits one token per forward pass, appends it to the sequence, then repeats. The loop is sequential and usually memory-bandwidth-bound.

Those phases produce different user-facing numbers. Time to first token (TTFT) captures queueing plus prefill. Tokens per second (TPS), or its inverse inter-token latency (ITL), describes the decode stream. A service can begin quickly and finish slowly—or the reverse—because the two phases stress different resources.

TTFT
Request arrival to the first visible token; dominated by queueing and prefill.
TPS / ITL
Decode throughput, or the delay between streamed tokens.
p50 / p90 / p99
The latency distribution, not one average. p99 exposes queueing, faults, and noisy neighbors.
The average tells you the machine is healthy. The tail tells you whether users agree.

A worked latency budget

A latency SLO becomes useful only after it is split into terms owned by different parts of the system.

Consider an illustrative interactive request with a ≈2,000-token prompt, an ≈500-token answer, ≈300 ms of prefill, and decode throughput of ≈50 tokens/s. Ignoring small overlap effects, model time is:

model latency ≈ 0.3 s + (500 tokens ÷ 50 tokens/s) = ≈10.3 s

Decode contributes ≈10 seconds—about 97% of model time in this example. A faster prefill improves the first visible response, but it barely changes completion time. A faster decode changes completion time directly. That distinction prevents a team from celebrating a TTFT improvement while the user still waits just as long for the full answer.

Ingress · ≈40 ms

TLS, gateway policy, and request parsing. Moved by network placement, connection reuse, and gateway capacity.

Queue · ≈110 ms

Waiting for an eligible replica. Moved by admission control, replica count, scheduling policy, and warm capacity; this term often dominates p99 before average utilization looks high.

Prefill · ≈300 ms

Prompt processing and initial KV construction. Moved by compute throughput, prompt length, batching, and prefill-pool capacity.

Decode · ≈10,000 ms

≈500 serial token steps at ≈50 tokens/s. Moved by HBM bandwidth, decode batching, model size and precision, and decode-pool capacity.

Egress · ≈50 ms

Streaming and client/network delivery. Moved by backpressure handling, network quality, and application behavior.

end-to-end ≈ 40 ms + 110 ms + 300 ms + 10,000 ms + 50 ms = ≈10.5 s

Two budgets should therefore be written separately. The first-token budget is ingress + queue + prefill + first-byte delivery, ≈500 ms here. The completion budget adds the decode stream, ≈10.5 seconds here. At capacity-review time, record both p50 and p99 for each term; otherwise queueing and fabric stalls disappear inside one opaque endpoint number.

The hardware mental model

A decoder-only transformer repeats a block containing masked self-attention and a feed-forward MLP, wrapped by normalization and residual connections. Attention creates the KV cache; the MLP holds much of the parameter mass. That is enough anatomy for infrastructure sizing.

The roofline model supplies the key mental shortcut: arithmetic intensity—operations performed per byte moved—determines whether performance is capped by compute or memory bandwidth. Prefill generally sits nearer the compute roof; autoregressive decode repeatedly streams weights and a growing KV cache, so it usually sits on the bandwidth slope.

The ridge point is the balance between peak compute and memory bandwidth. Left of it, adding arithmetic units cannot help if bytes arrive too slowly. Right of it, more bandwidth alone cannot exceed the compute ceiling. The plot is conceptual rather than a benchmark: the useful act is placing each phase with measurements from the target GPU and batch shape.

HBM

Capacity holds weights, KV cache, and buffers; bandwidth feeds the execution units during decode.

SMs

Streaming multiprocessors and Tensor Cores provide the compute budget that prefill can consume.

NVLink

GPU interconnect extends the execution domain when one device cannot hold or compute the model.

A Mixture-of-Experts (MoE) layer uses a router to send each token to only a few expert MLPs out of many. That reduces FLOPs per token, but not the resident weight set: for low-latency serving, all experts still need to be addressable. In other words, you can compute with ≈32B active parameters while provisioning HBM for the whole ≈1T model.

Inside a node, NVLink/NVSwitch provides the high-bandwidth GPU fabric. Across nodes, InfiniBand or Ethernet carries collectives and expert-routing traffic. Once tensor or expert parallelism crosses that boundary, the interconnect becomes part of the accelerator—and topology, congestion, and failure domains become model-performance concerns.

Do the math: what today’s open models actually require

Model selection is capacity planning. Before choosing a runtime, calculate the bytes that must live in HBM, the attention state each request adds, and the number of failure domains the replica crosses.

1 · WEIGHT MEMORY
parameters × bytes / parameter

BF16 = 2 bytes · FP8 = 1 byte · INT4 ≈ 0.5 byte. This is the floor, not the deployment budget.

2 · KV CACHE
≈ 2 × layers × kv_heads × head_dim × bytes

That is per token, per live sequence. Multiply by all live tokens; GQA and MLA reduce the stored key/value channels dramatically.

3 · GPU COUNT
ceil[(weights + live KV) ÷ 72 GB usable]

Here 72 GB is 90% of an 80 GB H100; the remaining 8 GB/GPU is reserved for runtime buffers, allocator fragmentation, and operational headroom.

4 · NODE COUNT
ceil(planned GPUs ÷ 8 GPUs / node)

Cross the eight-GPU boundary and the rack fabric joins the critical path. Power and cooling scale in the same step.

THE MoE RULE FOR LOW-LATENCY SERVING

In the fully GPU-resident scenario sized here, all experts stay in HBM while only the active experts drive compute per token. Offload to host memory or NVMe can reduce HBM demand, but adds traffic and latency. You provision the whole trillion for memory while burning ≈32B worth of FLOPs.

KV cache: the concurrency multiplier

Weights determine whether one replica fits. KV cache determines how many long-running requests that replica can serve at once.

For standard attention, the approximate BF16 KV bytes created per token are:

KV bytes / token ≈ 2 × layers × kv_heads × head_dim × bytes / element

The leading 2 stores both keys and values. Grouped-query attention reduces kv_heads; multi-head latent attention stores a compressed latent representation instead. Allocator metadata, block rounding, speculative branches, and other runtime buffers still require additional headroom.

LLAMA 3.1 405B · BF16 KV≈500 KB / token≈500 KB × ≈128K tokens ≈64 GB for one full-context request.
MLA-CLASS PLANNING VALUE≈70 KB / token≈70 KB × ≈128K tokens ≈9 GB for one full-context request.

Now apply concurrency. Eight simultaneous ≈128K-token sessions on the Llama example require ≈8 × 64 GB = ≈512 GB of KV cache. That is larger than the ≈405 GB FP8 weight set. On eight 80 GB H100s, the nominal 640 GB of HBM cannot hold ≈405 GB of weights plus ≈512 GB of live KV; the model may fit, but the workload does not.

The MLA-class planning value changes the shape: eight ≈128K sessions consume ≈72 GB of KV. That is still operationally meaningful, but it is no longer larger than the trillion-parameter weight set. Attention architecture is therefore an infrastructure input, not merely a model-quality detail.

CONCURRENCY LIMIT
floor(KV budget ÷ bytes per live sequence)

Use the admitted sequence length, not the advertised maximum context window.

LIVE-TOKEN BUDGET
Σ(prompt tokens + generated tokens)

Track active tokens across the whole replica. Averages hide the long sessions that trigger OOMs.

Capacity policy should state three numbers explicitly: maximum admitted context, maximum live tokens per replica, and the HBM reserve that cannot be allocated to KV. Without those limits, a few long-context prefills can evict useful cache blocks, stall admission, or crash the worker even when request count appears low.

Parallelism is a fabric decision

When a model or target throughput exceeds one GPU, the serving framework must divide work. The division method tells the network what kind of traffic it must carry and how a fault propagates.

ModeWhat it splitsUse it whenFabric demandCharacteristic failure
Tensor parallelismIndividual layer operations across GPUs.A layer or model cannot fit one GPU, or one GPU cannot meet latency.Frequent collectives; keep inside NVLink/NVSwitch where possible.One slow rank delays every collective; one rank loss takes down the replica.
Pipeline parallelismContiguous layer stages across GPUs or nodes.The model spans devices and stage balance is tractable.Activation transfer between stages; inter-node links can work with careful partitioning.Pipeline bubbles and the slowest stage cap throughput.
Expert parallelismMoE experts across devices.The full expert set exceeds a single memory domain.Token all-to-all traffic; topology and congestion are first-order concerns.Hot experts or skewed routing create stragglers and fabric hotspots.
Data parallelismIndependent requests across complete replicas.One replica fits and horizontal throughput is the goal.Low synchronization on the inference path; storage and ingress scale with replicas.Poor load balancing leaves one replica queued while others idle.

The default infrastructure preference is simple: fit tensor-parallel ranks inside one high-bandwidth GPU domain, then scale with independent replicas. Cross a node boundary only when model capacity or measured throughput requires it, because every added rank enlarges the synchronous failure domain.

Serving topology: separate unlike work

Disaggregation exists for one infrastructure reason: prefill and decode have different scaling curves. Separate pools let compute-heavy prompt processing scale without forcing the same replica count, GPU type, or batching policy onto bandwidth-heavy token generation. The cost is a new KV-transfer path and queue that must be capacity-limited, observed, and included in failure testing.

A short runtime pointer

Kernel fusion, speculative decoding, batching, caching, parallelism, and quantization all matter, but they are not the center of this pre-read. Treat them as ways to reshape the infrastructure bill: quantization lowers bytes per weight, caching trades compute for memory, batching raises utilization, and parallelism spends interconnect bandwidth. Part 2 of the visual study guide explains those mechanisms in detail.

The infrastructure bill of materials

Once the model footprint is known, a production replica becomes a concrete bill of materials—not an abstract endpoint.

Accelerators

Enough aggregate HBM for weights plus headroom, arranged into the smallest practical number of high-bandwidth NVLink or NVSwitch domains.

Host platform

CPU, RAM, PCIe lanes, NUMA topology, node-local NVMe, GPU passthrough, and a validated VM or bare-metal configuration.

Fabric

Low-latency, high-throughput east-west networking for collectives, expert routing, KV transfer, replica loading, and failure recovery.

Storage path

Durable object storage for immutable weight shards; NVMe staging for repeat loads; enough read throughput to hydrate replicas without turning a rollout into an outage.

Facility

A fully populated DGX H100 is rated at ≈10.2 kW maximum whole-system power. The two-node DeepSeek V3.1 and Kimi K2 sizing scenarios create a ≤≈20.4 kW IT load envelope before rack switching, external storage, and cooling/PUE.

Operations

Admission control, topology-aware placement, warm capacity, health gates, telemetry, upgrade sequencing, spare capacity, and rollback.

cold-start lower bound = model bytes ÷ effective end-to-end load bandwidth

A container being “Running” proves almost nothing. The replica is ready only after weight shards move from Objects to local NVMe, are verified, load into HBM, establish the distributed group, and pass a model-level health check. For the ≈1T-parameter Kimi K2 scenario, that path moves ≈1 TB before the first useful request.

The inference stack on Nutanix

The model server is only one process in a layered system. Nutanix contributes the operating envelopes, data services, network policy, and fleet view around it; each offering has a specific job rather than acting as a universal AI layer.

Figure 1 · The inference stack on Nutanix

Nutanix Enterprise AI

Defines the governed model-service layer: approved models, service endpoints, and the handoff between application consumers and the underlying serving estate. Its boundary should expose service policy without hiding GPU-capacity signals from operators.

NKP

Orchestrates inference pools on Kubernetes: GPU resource requests, topology-aware placement, rollout sequencing, health gates, replica policy, and separate prefill/decode pools when disaggregation is justified.

AHV

Provides the VM and host operating envelope for gateways, monitoring, tooling, and other infrastructure-adjacent services. GPU placement must align VM boundaries, passthrough choices, NUMA locality, and host-maintenance procedures.

Flow

Applies network policy and microsegmentation around ingress, control-plane services, storage paths, and GPU workers. The goal is explicit service boundaries without blocking the high-volume east-west paths the model actually needs.

Objects + Files

Objects is the immutable S3 model registry and durable blob store, with versioning and lifecycle policy around large artifacts. Files provides SMB/NFS semantics for shared, human- and tool-edited material that needs directories and in-place updates.

Prism

Provides the fleet view across compute and storage: capacity pressure, maintenance state, resource placement, and the shared blast radius behind an apparently healthy model endpoint.

Figure 2 · The weight lifecycle

Weight loading is a storage-and-network pipeline before it is a GPU operation. Every uncached replica must move and verify the same immutable bytes before it can serve.

cold-start lower bound = model bytes ÷ effective end-to-end load bandwidth

For an illustrative ≈400 GB FP8 weight set, an effective end-to-end load path of ≈5 GB/s gives ≈400 GB ÷ ≈5 GB/s = ≈80 seconds before checksum, allocation, distributed-group formation, graph initialization, and health checks. The slowest sustained stage—not the fastest device’s spec sheet—sets the floor. This is why a warm pool exists: it converts slow physical preparation into already-paid readiness.

Control loops, warm capacity, and two workload envelopes

NKP can scale decode replicas from signals such as queue depth and tail latency. But a new pod is not useful merely because it is scheduled: it may still need minutes to stage hundreds of gigabytes and load HBM. A warm pool of ready capacity is the shock absorber between the fast autoscaling decision and the slow physical cold start.

etcd belongs to the control plane, not the data plane. It holds small desired-state facts and pointers—such as “production → model v2,” replica counts, and routing rules. It should never hold weight blobs, chat history, or KV-cache payloads. Inference workers stay replaceable; durable bytes live in Objects or Files according to their access pattern.

That same separation supports two operating envelopes: AHV VMs for stateful or infrastructure-adjacent services, and NKP containers for elastic GPU inference. Across locations, NKP provides a consistent Kubernetes operating model for on-premises Nutanix and policy-approved public-cloud GPU capacity: keep governed data on-prem, and burst eligible compute when placement policy permits.

Objects → NVMe → HBM is the cold path. NVLink → fabric is the execution path. etcd and NKP coordinate the desired state; Prism shows the fleet.

Scaling, ownership, and failure modes

Autoscaling must react before users see a queue, but inference capacity can take tens of seconds or minutes to become usable.

A controller that observes only GPU utilization is late and sometimes wrong: decode can be bandwidth-bound while utilization looks moderate, and a queue can rise while new replicas are still loading. Use a small set of leading and confirming signals, and require a model-level readiness gate before routing traffic.

Failure modes worth designing before launch

HBM OOM during long-context prefill

Infra implication: enforce per-request context and per-replica live-token limits at admission; monitor KV allocation, not only request count.

NCCL or collective timeout

Infra implication: a tensor-parallel replica is one synchronous failure domain; capture rank-level timing and drain the entire replica when one participant degrades.

Tensor-parallel straggler

Infra implication: a single slow GPU, NUMA path, or link stretches every collective; topology-aware placement and per-rank telemetry are required.

Noisy neighbor on the shared fabric

Infra implication: collective and KV-transfer traffic need measurable capacity, isolation, and maintenance coordination with other east-west workloads.

etcd quorum loss

Infra implication: existing workers may continue serving, but desired-state changes and rollouts can freeze; keep payloads out of etcd and test control-plane recovery separately.

Thundering-herd cold start

Infra implication: a deploy or node loss can make many replicas fetch the same hundreds of gigabytes; use warm capacity, staged rollout, local caching, and storage-load limits.

Partial model hydration

Infra implication: never advertise readiness after the container starts; require digest verification, complete HBM load, distributed-group formation, and an inference health check.

Node drain crosses the SLO margin

Infra implication: maintenance capacity is part of steady-state sizing. A replica that spans nodes may disappear as a unit when one node drains.

The operational test is not “Can Kubernetes restart it?” It is “Can the fleet replace this replica, move its bytes, reform its communication group, and absorb traffic without violating the user-facing SLO?”

Artifacts: what training leaves behind

A trained model is not one file. A typical release directory includes architecture and generation configuration, tokenizer assets, documentation, and weight shards. A simplified layout looks like this:

model-v2/
├── config.json # architecture and dimensions
├── generation_config.json # decoding defaults
├── model-00001-of-000xx.safetensors
├── model.safetensors.index.json # shard map
├── tokenizer.json / tokenizer_config.json
├── special_tokens_map.json
└── README.md # model card and usage notes

Training checkpoints are larger still. Besides one copy of the weights, Adam-family optimization commonly maintains first- and second-moment state—roughly two additional model-sized sets—plus scheduler and random-number-generator state. The shorthand is ≈1× weights + ≈2× optimizer state, before format and precision details. Checkpoint storage can therefore dwarf the final serving artifact.

LoRA adapters take the opposite approach: keep a frozen base model and store small learned matrices per task. The adapter is cheap to copy and promote, but it is meaningful only alongside the exact compatible base model.

Serving then creates its own artifacts. Chat history is application state. Prefix-cache snapshots or reusable KV blocks are performance state. Logs, traces, evaluation outputs, and safety records are operational state. “Stateless inference” usually means the worker can be replaced—not that the surrounding system has no state.

The clean promotion pattern is to keep each model build immutable in Objects and move a small mutable pointer in etcd. Promotion becomes a metadata flip from one content-addressed or versioned artifact to another; rollback is the reverse flip. Workers resolve the pointer, stage the referenced bytes, verify them, and only then take traffic.

Files vs Objects: the one rule

Nutanix Files

SMB / NFS · mounted hierarchy

Files supports folders, in-place edits, byte-range locking, and multiple writers coordinating through familiar filesystem semantics. It is the shared working space.

Nutanix Objects

S3 API · buckets and keys

Objects fits write-once/read-many blobs addressed over HTTPS. Versioning and lifecycle policy make it the durable registry, while application logic owns concurrency.

If your app speaks S3, it wants Objects; if a human or tool needs a mounted drive with folders and in-place edits, it wants Files.

Capacity-planning checklist

A defensible deployment plan can be reviewed as eight linked calculations. If one input is unknown, mark it as a measurement task rather than filling the gap with a vendor peak number.

  1. Choose the exact model build. Record architecture, total and active parameters, precision, context limit, attention design, license, weight format, and immutable artifact digest. “405B” is not enough if one build is BF16 and another FP8.
  2. Compute the resident weight footprint. Multiply parameters by bytes per parameter, then add measured runtime reserve for graph state, kernels, temporary buffers, and fragmentation. Round to a supported GPU topology—not merely the mathematical minimum.
  3. Budget KV cache from context × concurrency. Calculate bytes per token from the architecture, then multiply by the maximum admitted live tokens per replica. State context limits and the scheduling policy that enforces them.
  4. Select GPU and node count. Fit weights + KV + reserve into usable HBM. Prefer the fewest high-bandwidth domains that meet latency; record the spare capacity required for maintenance and failover.
  5. Validate the fabric. Map tensor, pipeline, expert, and KV-transfer traffic onto actual links. Benchmark the intended topology under contention, and identify every synchronous failure domain.
  6. Size storage and the cold path. Budget durable capacity for weights, checkpoints, adapters, snapshots, and retention copies. Divide rollout bytes by required rollout time to derive aggregate read throughput; include concurrent hydrations.
  7. Reserve power and cooling. Use node-level maximum envelopes plus switching, storage, and facility overhead. Check rack density, power feeds, cooling, and maintenance capacity before treating GPU inventory as deployable.
  8. Set the warm-pool and rollout policy. Compare demand growth and failure-recovery objectives with measured hydrate-and-initialize time. Pre-stage enough ready capacity to cover that gap, then canary, health-gate, and roll forward in bounded waves.

The final unit of capacity is not a GPU. It is a healthy replica, loaded with the right artifact, inside a tested failure domain, with enough HBM and fabric headroom to meet the SLO.

Putting it together: one operating model

A request enters through a gateway and lands on NKP-managed GPU capacity. In a disaggregated design, a compute-oriented prefill pool builds KV state and hands it across a fast fabric to a bandwidth-oriented decode pool; the two pools can be scheduled and scaled independently. Approved weights travel from Objects through node-local NVMe into HBM. Shared human-edited material belongs on Files, etcd carries only small desired-state pointers, and Prism provides the fleet view.

Warm GPU capacity keeps sudden demand off the cold-start path. AHV-hosted ancillary services and NKP-managed inference pools can share the same storage and observability foundation, while policy decides whether eligible overflow remains on-premises or uses public-cloud GPU capacity.

Inference engineering is infrastructure engineering

Choosing a model is choosing the physical shape of the service.

parameter count → GPU count → node count → NVLink domains → inter-node fabric → power, cooling & floor space
≤≈20.4 kW

Maximum whole-system IT load across two occupied DGX H100-class nodes; cooling/PUE is additional.

≈1 TB

Kimi K2 FP8 weight data crossing Objects → NVMe → HBM for every uncached replica load.

≈512 GB

KV cache for eight ≈128K-token Llama 405B sessions at the ≈500 KB/token planning value.

That is the core argument. Cold start is a storage and network throughput problem. Expert parallelism is a fabric problem. Long context multiplied by concurrency is an HBM capacity problem. Replica density is a power, cooling, and scheduling problem. The runtime exposes these pressures; infrastructure determines whether the service survives them.

Small glossary

Prefill
Parallel processing of the input prompt that builds initial attention state.
Decode
The serial loop that generates one token at a time.
TTFT
Time to first token: queueing plus prefill latency as the user experiences it.
TPS / ITL
Tokens per second, or inter-token latency, during decode.
Roofline model
A performance model that relates arithmetic intensity to the ceilings imposed by memory bandwidth and peak compute.
Serving framework
The service layer that queues, batches, schedules, and executes model requests on accelerators.
KV cache
Stored key/value projections of prior tokens, reused by later decode steps.
Quantization
Representing weights or activations with fewer bits to reduce memory and traffic.
Tensor parallelism
Splitting a layer’s tensor operations across tightly connected accelerators.
MoE
Mixture-of-Experts: sparse layers that route each token to a subset of expert MLPs.
Speculative decoding
Drafting tokens with a small model and verifying them in parallel with a larger one.
Cold start
The path from an unavailable replica to one with initialized weights ready in HBM.
LoRA
Small task-specific low-rank adapter weights applied to a frozen base model.
SafeTensors
A tensor serialization format commonly used for sharded model weights.
Disaggregation
Running prefill and decode on separately sized worker pools.
Warm pool
Ready, already-loaded inference capacity held to absorb demand without waiting for a full model cold start.
SM
Streaming multiprocessor: the GPU execution unit that contains CUDA and Tensor Cores.
HBM
High-bandwidth memory attached to the accelerator; the capacity pool that must hold weights, caches, and runtime overhead.
GQA / MLA
Attention designs that reduce KV-cache size by storing fewer or compressed key/value channels.
Expert parallelism
Distributing MoE experts across accelerators; token routing then becomes a fabric operation.
Pipeline parallelism
Assigning consecutive model-layer stages to different accelerators and passing activations between them.
Data parallelism
Running complete model replicas that independently serve different requests.
Collective
A coordinated multi-rank communication operation such as all-reduce or all-to-all.
Live tokens
The prompt and generated tokens currently occupying KV-cache capacity across admitted sequences.
Ridge point
The roofline balance where the bandwidth slope meets the compute ceiling.
NVLink domain
The set of GPUs joined by NVIDIA’s high-bandwidth accelerator interconnect, typically inside one server.
etcd
A consistent control-plane key-value store for small cluster state and pointers—not blobs.
