How to use this guide

This is the team’s systems-level map of inference: the path from an incoming request to generated tokens, and the infrastructure required to make that path predictable.

Read it straight through for the overall architecture, or use it as a field reference during sizing, design review, and incident response. The center of gravity is infrastructure: HBM capacity, GPU topology, east-west fabric, storage throughput, failure domains, power, scheduling, and the Nutanix operating model. Runtime techniques appear only where they materially change that bill.

The story runs in one direction. It starts with a 124M-parameter GPT-2 running on a laptop, where every inference concept is visible in about 130 lines of Python. It then scales the same concepts to trillion-parameter models, where each line of that script turns into a hardware, storage, or network decision. It ends in the Nutanix AI Factory: Project Astra turns bare GPU servers into managed capacity, COCI clusters and AHV operate the GPU nodes, NKP runs Kubernetes on them, Nutanix Enterprise AI (NAI) serves the models, and Nutanix Files and Objects hold the bytes.

Start small: GPT-2 on a laptop

Every large-scale inference problem already exists in a 124M-parameter model. It is just too small to hurt.

The companion script gpt2-inference.py runs GPT-2 with no serving framework: a hand-written BPE tokenizer, an explicit transformer forward pass, top-p sampling, and a generation loop. Read it with this map in mind, because each step reappears later as infrastructure.

The script deliberately omits the single most important production optimization: it has no KV cache. Every decode step re-runs attention over the entire sequence, so the work per step grows with length. A production engine such as vLLM stores each layer's keys and values once and processes only the newest token. That trade saves recomputation and spends GPU memory instead, and the rest of this guide is largely about paying that memory bill.

GPT-2 124M · FP32≈550 MB weights12 layers · 12 heads · 768 hidden · 1,024-token context. Fits in laptop RAM with room to spare.
GPT-2 KV CACHE · FP32≈72 KB / token2 × 12 layers × 12 heads × 64 dims × 4 bytes. ≈72 MB for a full 1,024-token context.

Hold on to that ≈72 KB/token figure. A trillion-parameter MLA model later in this guide stores roughly the same amount per token. The per-token cost barely changed. What changed is context length (128K instead of 1K), concurrency (thousands of sessions instead of one), and weights that no longer fit in one device. Those three multipliers are why inference becomes an infrastructure problem.

How an inference request behaves

Training is a long, throughput-oriented batch job that changes model parameters. Inference holds those parameters fixed and answers requests online. The path is layered: an application calls an API gateway; the gateway routes to a serving framework such as vLLM or TensorRT-LLM; the framework drives model execution; and the runtime finally schedules work onto GPU hardware. The serving-framework layer is where our team will operate the service, but every layer beneath it can set the latency ceiling. On Nutanix, the gateway is the NAI Agent Gateway built on Envoy, the serving layer is KServe driving vLLM or NVIDIA NIM containers, and those containers run on NKP worker nodes with GPUs attached through AHV.

PREFILL

The prompt is processed largely in parallel to build attention state. This phase is rich in matrix work and is usually compute-bound.

DECODE

The model emits one token per forward pass, appends it to the sequence, then repeats. The loop is sequential and usually memory-bandwidth-bound.

Those phases produce different user-facing numbers. Time to first token (TTFT) captures queueing plus prefill. Tokens per second (TPS), or its inverse inter-token latency (ITL), describes the decode stream. A service can begin quickly and finish slowly—or the reverse—because the two phases stress different resources.

TTFT
Request arrival to the first visible token; dominated by queueing and prefill.
TPS / ITL
Decode throughput, or the delay between streamed tokens.
p50 / p90 / p99
The latency distribution, not one average. p99 exposes queueing, faults, and noisy neighbors.

These numbers are available directly on the platform. NAI endpoint metrics report TTFT, time per output token (TPOT, the same quantity as ITL), output tokens per second, request latency, and token usage. They can be filtered by API key, are backed by Prometheus, and can be exported over OpenTelemetry. Per-phase SLOs are therefore something the team can measure and enforce, not just a concept.

The average tells you the machine is healthy. The tail tells you whether users agree.

A worked latency budget

A latency SLO becomes useful only after it is split into terms owned by different parts of the system.

Consider an illustrative interactive request with a ≈2,000-token prompt, an ≈500-token answer, ≈300 ms of prefill, and decode throughput of ≈50 tokens/s. Ignoring small overlap effects, model time is:

model latency ≈ 0.3 s + (500 tokens ÷ 50 tokens/s) = ≈10.3 s

Decode contributes ≈10 seconds—about 97% of model time in this example. A faster prefill improves the first visible response, but it barely changes completion time. A faster decode changes completion time directly. That distinction prevents a team from celebrating a TTFT improvement while the user still waits just as long for the full answer.

Ingress · ≈40 ms

TLS, gateway policy, and request parsing. Moved by network placement, connection reuse, and gateway capacity.

Queue · ≈110 ms

Waiting for an eligible replica. Moved by admission control, replica count, scheduling policy, and warm capacity; this term often dominates p99 before average utilization looks high.

Prefill · ≈300 ms

Prompt processing and initial KV construction. Moved by compute throughput, prompt length, batching, and prefill-pool capacity.

Decode · ≈10,000 ms

≈500 serial token steps at ≈50 tokens/s. Moved by HBM bandwidth, decode batching, model size and precision, and decode-pool capacity.

Egress · ≈50 ms

Streaming and client/network delivery. Moved by backpressure handling, network quality, and application behavior.

end-to-end ≈ 40 ms + 110 ms + 300 ms + 10,000 ms + 50 ms = ≈10.5 s

Two budgets should therefore be written separately. The first-token budget is ingress + queue + prefill + first-byte delivery, ≈500 ms here. The completion budget adds the decode stream, ≈10.5 seconds here. At capacity-review time, record both p50 and p99 for each term; otherwise queueing and fabric stalls disappear inside one opaque endpoint number.

The hardware mental model

A decoder-only transformer repeats a block containing masked self-attention and a feed-forward MLP, wrapped by normalization and residual connections. Attention creates the KV cache; the MLP holds much of the parameter mass. That is enough anatomy for infrastructure sizing.

The roofline model supplies the key mental shortcut: arithmetic intensity—operations performed per byte moved—determines whether performance is capped by compute or memory bandwidth. Prefill generally sits nearer the compute roof; autoregressive decode repeatedly streams weights and a growing KV cache, so it usually sits on the bandwidth slope.

The ridge point is the balance between peak compute and memory bandwidth. Left of it, adding arithmetic units cannot help if bytes arrive too slowly. Right of it, more bandwidth alone cannot exceed the compute ceiling. The plot is conceptual rather than a benchmark: the useful act is placing each phase with measurements from the target GPU and batch shape.

HBM

Capacity holds weights, KV cache, and buffers; bandwidth feeds the execution units during decode.

SMs

Streaming multiprocessors and Tensor Cores provide the compute budget that prefill can consume.

NVLink

GPU interconnect extends the execution domain when one device cannot hold or compute the model.

A Mixture-of-Experts (MoE) layer uses a router to send each token to only a few expert MLPs out of many. That reduces FLOPs per token, but not the resident weight set: for low-latency serving, all experts still need to be addressable. In other words, you can compute with ≈32B active parameters while provisioning HBM for the whole ≈1T model.

Inside a node, NVLink/NVSwitch provides the high-bandwidth GPU fabric. Across nodes, InfiniBand or Ethernet carries collectives and expert-routing traffic. Once tensor or expert parallelism crosses that boundary, the interconnect becomes part of the accelerator—and topology, congestion, and failure domains become model-performance concerns.

GPU memory and bandwidth: the two numbers that matter

For inference, a GPU is mostly described by two numbers: how many bytes its memory holds, and how fast it can read them.

Capacity decides whether a model and its KV cache fit. Bandwidth decides how fast decode can run once they do. At batch size 1, every decode step must read every active weight once, which gives a hard ceiling that no kernel optimization can beat:

decode ceiling tokens/s per stream ≤ aggregate memory bandwidth ÷ active-weight bytes read per token
DENSE · LLAMA 3.1 405B FP8 · 8×H100
≈26.8 TB/s ÷ ≈405 GB ≈ 66 tok/s

That is the theoretical ceiling before KV reads, collectives, and kernel overhead. It is why the ≈50 tokens/s figure in the latency budget above is realistic, not pessimistic.

DENSE · 70B FP8 · 1× RTX PRO 6000
≈1.6 TB/s ÷ ≈70 GB ≈ 23 tok/s

The model fits in 96 GB, but GDDR7 bandwidth caps every stream. Capacity and bandwidth are separate purchasing decisions.

MoE · GPT-OSS-120B MXFP4 · 1× RTX PRO 6000
≈1.6 TB/s ÷ ≈3 GB ≈ 530 tok/s

Only ≈5.1B active parameters are read per token, and most of them are ≈4.25-bit expert weights, so the ceiling rises by an order of magnitude. MoE shifts the pressure from bandwidth to capacity and routing.

Do the math: what today’s open models actually require

Model selection is capacity planning. Before choosing a runtime, calculate the bytes that must live in HBM, the attention state each request adds, and the number of failure domains the replica crosses.

1 · WEIGHT MEMORY
parameters × bytes / parameter

BF16 = 2 bytes · FP8 = 1 byte · INT4 ≈ 0.5 byte. This is the floor, not the deployment budget.

2 · KV CACHE
≈ 2 × layers × kv_heads × head_dim × bytes

That is per token, per live sequence. Multiply by all live tokens; GQA and MLA reduce the stored key/value channels dramatically.

3 · GPU COUNT
ceil[(weights + live KV) ÷ 72 GB usable]

Here 72 GB is 90% of an 80 GB H100; the remaining 8 GB/GPU is reserved for runtime buffers, allocator fragmentation, and operational headroom.

4 · NODE COUNT
ceil(planned GPUs ÷ 8 GPUs / node)

Cross the eight-GPU boundary and the rack fabric joins the critical path. Power and cooling scale in the same step.

THE MoE RULE FOR LOW-LATENCY SERVING

In the fully GPU-resident scenario sized here, all experts stay in HBM while only the active experts drive compute per token. Offload to host memory or NVMe can reduce HBM demand, but adds traffic and latency. You provision the whole trillion for memory while burning ≈32B worth of FLOPs.

Choosing a GPU SKU really means choosing how many failure domains a replica spans.

The jump from one node to two changes the problem qualitatively. Tensor collectives and expert routing leave the NVLink domain; replica placement now consumes rack-level power, cooling, and fabric; and any failure or drain operation can move a near-terabyte service footprint.

KV cache: the concurrency multiplier

Weights determine whether one replica fits. KV cache determines how many long-running requests that replica can serve at once.

For standard attention, the approximate BF16 KV bytes created per token are:

KV bytes / token ≈ 2 × layers × kv_heads × head_dim × bytes / element

The leading 2 stores both keys and values. Grouped-query attention reduces kv_heads; multi-head latent attention stores a compressed latent representation instead. Allocator metadata, block rounding, speculative branches, and other runtime buffers still require additional headroom.

LLAMA 3.1 405B · BF16 KV≈500 KB / token≈500 KB × ≈128K tokens ≈64 GB for one full-context request.
MLA-CLASS PLANNING VALUE≈70 KB / token≈70 KB × ≈128K tokens ≈9 GB for one full-context request.

Now apply concurrency. Eight simultaneous ≈128K-token sessions on the Llama example require ≈8 × 64 GB = ≈512 GB of KV cache. That is larger than the ≈405 GB FP8 weight set. On eight 80 GB H100s, the nominal 640 GB of HBM cannot hold ≈405 GB of weights plus ≈512 GB of live KV; the model may fit, but the workload does not.

The MLA-class planning value changes the shape: eight ≈128K sessions consume ≈72 GB of KV. That is still operationally meaningful, but it is no longer larger than the trillion-parameter weight set. Attention architecture is therefore an infrastructure input, not merely a model-quality detail.

CONCURRENCY LIMIT
floor(KV budget ÷ bytes per live sequence)

Use the admitted sequence length, not the advertised maximum context window.

LIVE-TOKEN BUDGET
Σ(prompt tokens + generated tokens)

Track active tokens across the whole replica. Averages hide the long sessions that trigger OOMs.

Capacity policy should state three numbers explicitly: maximum admitted context, maximum live tokens per replica, and the HBM reserve that cannot be allocated to KV. Without those limits, a few long-context prefills can evict useful cache blocks, stall admission, or crash the worker even when request count appears low.

What NAI does with the KV cache today

Once KV cache is the concurrency limit, two platform features matter: sending a request to the replica that already holds its prefix, and spilling cold cache blocks somewhere cheaper than HBM. NAI 2.8 ships early versions of both.

KV-cache-aware routing · Tech Preview

vLLM workers publish KV-cache events. The open-source llm-d inference scheduler, running as the Gateway API Inference Extension's endpoint picker (EPP), indexes which prefixes each replica holds and scores replicas on prefix match, KV utilization, queue depth, and active requests. Envoy in the Agent Gateway then forwards the request. For agents that resend a long system prompt and tool schema on every turn, a prefix hit skips most of prefill and cuts TTFT. It works only for local, same-cluster endpoints and cannot be combined with multi-node endpoints or KV offload.

KV-cache offload · Tech Preview

Evictable KV blocks spill from GPU memory to host RAM (a memory-backed /dev/shm region) instead of being discarded, so a returning conversation avoids a full re-prefill. It is limited to vLLM, single-node, GPU-passthrough endpoints, and it requires at least 1.2× the GPU memory per GPU in host RAM. That is a real sizing input: on an 8×H200 node, 1.2 × 141 GB × 8 ≈ 1.35 TB of host RAM set aside for the cache. This improves repeat-prompt TTFT, not decode speed.

Roadmap · tiered and shared KV

The Nutanix AI-storage architecture extends the hierarchy to GPU HBM → host RAM → local NVMe → a remote, distributed Nutanix block store, using NVIDIA NIXL for the data path. The goal is a persistent, cross-node KV cache that prefill and decode pools can share. This is design direction, not shipped NAI behavior.

Parallelism is a fabric decision

When a model or target throughput exceeds one GPU, the serving framework must divide work. The division method tells the network what kind of traffic it must carry and how a fault propagates.

ModeWhat it splitsUse it whenFabric demandCharacteristic failure

The default infrastructure preference is simple: fit tensor-parallel ranks inside one high-bandwidth GPU domain, then scale with independent replicas. Cross a node boundary only when model capacity or measured throughput requires it, because every added rank enlarges the synchronous failure domain.

NAI follows the same order. Tensor parallelism inside one node is the standard vLLM path. Multi-node serving, which uses pipeline parallelism across nodes via KServe's LLMInferenceService and a LeaderWorkerSet of pods, is a Tech Preview in NAI 2.8. It cannot be combined with speculative decoding or KV-cache offload. Model replicas (data parallelism) are scaled as endpoint instances.

Serving topology: separate unlike work

Disaggregation exists for one infrastructure reason: prefill and decode have different scaling curves. Separate pools let compute-heavy prompt processing scale without forcing the same replica count, GPU type, or batching policy onto bandwidth-heavy token generation. The cost is a new KV-transfer path and queue that must be capacity-limited, observed, and included in failure testing.

Where Nutanix is today: prefill/decode disaggregation is not a generally available NAI feature. The underlying NAI KServe integration already includes an LLMInferenceService example with separate prefill and decode vLLM workers coordinated by the llm-d endpoint picker, and the NAI roadmap names P/D disaggregation, followed by shared caching, as a next step. Design reviews should treat the figure above as the target shape and plan today's endpoints as unified replicas.

A short runtime pointer

Kernel fusion, speculative decoding, batching, caching, parallelism, and quantization all matter, but they are not the center of this pre-read. Treat them as ways to reshape the infrastructure bill: quantization lowers bytes per weight, caching trades compute for memory, batching raises utilization, and parallelism spends interconnect bandwidth. In NAI, most of these are exposed as vLLM engine arguments on the endpoint, validated at creation time in 2.8, with speculative decoding as a supported option. Part 2 of the visual study guide explains those mechanisms in detail.

The infrastructure bill of materials

Once the model footprint is known, a production replica becomes a concrete bill of materials—not an abstract endpoint.

Accelerators

Enough aggregate HBM for weights plus headroom, arranged into the smallest practical number of high-bandwidth NVLink or NVSwitch domains.

Host platform

CPU, RAM (including ≥1.2× GPU memory per GPU if NAI KV offload is enabled), PCIe lanes, NUMA topology, node-local NVMe, AHV GPU passthrough or vGPU, and a validated VM or bare-metal configuration.

Fabric

Low-latency, high-throughput east-west networking for collectives, expert routing, KV transfer, replica loading, and failure recovery, kept separate from north–south Flow VPC traffic.

Storage path

Objects for durable model imports, corpora, and checkpoints; a Files RWX share as the live model repository every replica reads; enough aggregate read throughput (NFS over RDMA where available) to load replicas without turning a rollout into an outage.

Facility

A fully populated DGX H100 is rated at ≈10.2 kW maximum whole-system power. The two-node DeepSeek V3.1 and Kimi K2 sizing scenarios create a ≤≈20.4 kW IT load envelope before rack switching, external storage, and cooling/PUE.

Operations

Admission control, topology-aware placement, warm capacity, health gates, telemetry, upgrade sequencing, spare capacity, and rollback.

cold-start lower bound = model bytes ÷ effective end-to-end load bandwidth

A container being “Running” proves almost nothing. The replica is ready only after weight shards stream from the shared model repository, load into HBM, allocate KV blocks, establish the distributed group, and pass a model-level health check. For the ≈1T-parameter Kimi K2 scenario, that path moves ≈1 TB before the first useful request.

The inference stack on Nutanix

The model server is only one process in a layered system. Nutanix contributes everything around it: hardware bring-up, the GPU-node control plane, virtualization, Kubernetes, the model-serving platform, storage, and network policy. Each offering has a specific job rather than acting as a universal AI layer. The umbrella that packages them into an AI Factory is Project Astra.

Project Astra: from GPU server to inference endpoint

Astra is Nutanix's AI Factory program. Its promise is "user intent → ready-to-use GPU or inference service": discovery, imaging, GPU allocation, VM provisioning, tenancy, storage, networking, drivers, and validation happen behind one orchestrated workflow instead of a runbook. It targets two audiences: neoclouds and service providers selling GPU-, VM-, Kubernetes-, and token-as-a-service to many tenants, and enterprises building on-premises AI Factories without assembling the stack by hand. Astra 1.0 is targeting general availability in January 2027, and Astra 1.2 in March 2027.

GPU servers → Foundation Central + Nico (discover, health-check, image) → NIM (claim, build clusters) → AHV + COCI (GPU VMs) → Prism Central projects & resource groups (tenancy) → NKP (workload clusters) → NAI (endpoints)

In this chain, NIM is the Nutanix infrastructure manager, not NVIDIA's NIM inference microservices, which appear later inside NAI. The division of labor is the important part: Astra provisions and operates the infrastructure; NKP provides Kubernetes; NAI deploys, governs, and serves models. The inference-specific problems in this guide (GPU topology, fabric isolation, capacity, lifecycle) are Astra's problems. Endpoint creation, routing, and model governance are NAI's.

COCI: a control plane built for GPU nodes

A classic Nutanix HCI cluster runs a storage data path on every node. GPU servers do not need one. Their job is to keep accelerators busy, and every CPU core or NVMe drive spent on a distributed storage fabric is a cost. COCI (Centralized Operations for Cluster Infrastructure) is the answer: a lightweight cluster control plane, typically three pods running on a Zagreus cluster, that Prism Central sees as a compute cluster.

What it runs

VM management and hypervisor services (Genesis, Acropolis) for compute-only GPU nodes: VM scheduling, GPU-node lifecycle and health, expansion, upgrades, and v4 APIs. The design target is ≈128 GPU nodes per COCI cluster, bounded by subsystem and blast-radius limits.

What it does not run

No HCI storage data path and no model serving. GPU-node VMs boot from volumes exported by a separate infrastructure cluster over CCVS (Cross-Cluster Volume Storage) and iSCSI, so storage capacity scales independently of GPU capacity.

Why inference cares

A COCI cluster is a failure and maintenance domain. Its size bounds how many GPU nodes one control-plane incident or upgrade can touch. Each GPU node belongs to exactly one COCI cluster, and topology-aware node selection (which nodes share NVLink or a leaf switch) is still being modeled explicitly.

Nutanix Enterprise AI (NAI)

A Kubernetes-native platform for deploying and governing LLM endpoints. An operator picks a model from the validated catalog (Hugging Face, NVIDIA NGC/NIM, or a manual import); NAI selects the runtime and GPU profile, calculates resources, creates KServe objects and storage, and exposes an OpenAI-compatible endpoint with an API key. NAI 2.8 (August 2026) adds fine-grained RBAC and model sharing, generally available fine-tuning and MCP server management, air-gapped and non-catalog NIM import, and Tech Previews of multi-node inference, KV-aware routing, and KV offload. It runs on NKP and, per 2.8 material, on EKS, AKS, and GKE.

NKP

Runs the management and workload Kubernetes clusters that host NAI. For inference it provides dedicated GPU node pools with their own images, labels, and taints, and the NVIDIA GPU Operator (driver, container toolkit, device plugin, GPU Feature Discovery, MIG Manager, DCGM exporter). The node-pool autoscaler can add GPU workers, but only if AHV has compatible free GPUs. AI Navigator, NKP's conversational ops assistant, helps troubleshoot pending pods and missing GPU resources.

AHV

Attaches GPUs to NKP worker VMs. Whole-GPU passthrough is the default for large or multi-GPU models. Passthrough plus MIG inside the guest gives isolated fractional GPUs (MIG-backed vGPU profiles are not supported for NKP VMs). vGPU trades performance and licensing for consolidation. Astra adds GPU topology exposure to VMs, device bundles that pair GPUs with their east-west NICs, and topology-aware placement, because NUMA, PCIe, and NVLink locality decide tensor-parallel speed.

COCI

The GPU-node control plane described above: compute-only nodes, VM lifecycle, and health at ≈128-node scale, with no HCI data path.

Flow

Provides per-tenant VPCs, subnets, and security policy for north–south and Kubernetes traffic, scoped to Prism Central projects. It deliberately does not sit in the GPU collective path; that fabric is isolated by InfiniBand partition keys or switch segmentation.

Files

The live model repository. NAI creates one ReadWriteMany PVC per model on a Files share (NFSv4 through the Nutanix CSI driver), and every replica's vLLM or NIM pod mounts it at /mnt/models. The Files AI Performance Profile adds SR-IOV, iSER, and NFS over RDMA to shorten weight loading. Nutanix Unified Storage material cites ≈10 GB/s sequential read per node, with ≈20 GB/s per node on the NFS-over-RDMA roadmap.

Objects

The durable, S3-compatible source. It holds model imports (including air-gapped NIM imports), RAG corpora, datasets, fine-tuning checkpoints, logs, and archives. It is where bytes arrive and are retained, not where replicas read from on every start. A published four-node all-flash benchmark reached ≈14 GB/s with 8 MB objects; S3 over RDMA is emerging.

Prism Central

Holds projects and resource groups (the tenancy boundary for GPUs and networks in Astra) and provides the fleet view: capacity pressure, maintenance state, placement, and the shared blast radius behind an apparently healthy endpoint.

Figure 2 · The weight lifecycle in NAI

Weight loading is a storage-and-network pipeline before it is a GPU operation. In NAI, bytes are written once into a shared Files volume and then read by every replica that starts, which makes the Files read path the cold-start path.

cold-start lower bound = model bytes ÷ effective end-to-end load bandwidth

For an illustrative ≈400 GB FP8 weight set, a Files node sustaining the ≈10 GB/s sequential read cited for Nutanix Unified Storage gives ≈400 GB ÷ ≈10 GB/s = ≈40 seconds as the floor, before deserialization, KV allocation, NCCL group formation, graph capture, and health checks. At a more typical ≈5 GB/s effective path it is ≈80 seconds. Measured reality can be much worse. Internal troubleshooting logs have recorded vLLM taking ≈140 seconds to load ≈40 GB of a 4-bit 70B model on L40S, an effective ≈0.3 GB/s, because deserialization and quantization handling, not storage, dominated. The slowest sustained stage sets the floor, so measure the load, don't derive it from a spec sheet.

Two levers move this number on Nutanix. NFS over RDMA with the Files AI Performance Profile shortens the network and virtualization overhead of the read. GPUDirect Storage, which moves data from storage into GPU memory without bouncing through host RAM, cut a 13B model load from ≈12.7 s to ≈3.9 s in a Nutanix Unified Storage test; GDS loading into NAI is tracked work, not a shipped feature. KServe's LocalModelCache can also pre-stage copies onto node-local disks, but it is opt-in; the default NAI path reads over the Files mount.

Control loops, warm capacity, and two workload envelopes

Autoscaling happens at two levels, and on Nutanix today they behave differently. At the endpoint level, NAI supports manual scaling of endpoint instances without downtime and hibernation, which releases an endpoint's GPUs and resumes it later. Knative scale-to-zero is explicitly disabled in the supported configuration, because a scale-from-zero event is a full cold start. Metric-driven autoscaling (HPA and KEDA on Prometheus signals) exists in Nutanix's KServe codebase but is not a standard NAI 2.8 feature. At the node level, the NKP cluster autoscaler can add GPU worker VMs when pods are pending, but it cannot create GPUs: it succeeds only if COCI and AHV have compatible free GPUs, images, and licenses.

In either case, a new pod is not useful merely because it is scheduled. It may still need minutes to read hundreds of gigabytes from Files and load HBM. A warm pool of already-loaded endpoint instances is the shock absorber between a fast scaling decision and a slow physical cold start. Hibernation is the tool for the opposite case: releasing capacity for endpoints whose users can tolerate a resume delay.

etcd belongs to the control plane, not the data plane. It holds small desired-state facts and pointers—such as “production → model v2,” replica counts, and routing rules. It should never hold weight blobs, chat history, or KV-cache payloads. Inference workers stay replaceable; durable bytes live in Objects or Files according to their access pattern.

That same separation supports two operating envelopes: AHV VMs for stateful or infrastructure-adjacent services, and NKP containers for elastic GPU inference. Across locations, NAI provides a consistent serving layer on NKP on-premises and on supported public-cloud Kubernetes (EKS, AKS, GKE): keep governed data and models on-premises, and burst eligible workloads when placement policy permits.

Objects → Files → HBM is the cold path. NVLink → east-west fabric is the execution path. Astra and COCI make GPUs exist; NKP schedules them; NAI turns them into endpoints; Prism Central shows the fleet.

Nutanix already runs this stack for its own engineers, and the results match the arithmetic in this guide.

Internal IT operates a GPU Farm that serves Token-as-a-Service (TaaS) to Nutanix developers, mostly for coding agents running in editors and terminals, plus chat, RAG, embeddings, and reranking. A developer requests a key from an internal token portal, which calls NAI to mint it. From then on, the NAI gateway handles authentication, model authorization, quotas, rate limits, routing, and token accounting. The client never learns which GPU, node, or replica served it.

The lessons so far map directly onto earlier sections:

  1. Capacity is cheap; interconnect is not. A 96 GB card holds a lot of model, which makes RTX PRO 6000 an economical way to serve single-GPU MoE models. But without NVLink, tensor parallelism across cards pushes every all-reduce and KV movement over PCIe, which materially hurts inter-token latency for 30B–120B-class models. This is the "interconnect column" from the GPU table, observed in production.
  2. MoE plus one GPU is the sweet spot. gpt-oss-120b fits on one card in native MXFP4. For the agent platform, the team chose Qwen3.6-35B-A3B on a single RTX PRO 6000: ≈3B active parameters give a high decode ceiling, and no tensor parallelism means no PCIe collective penalty.
  3. Benchmark quality isn't agent compatibility. gpt-oss-120b was acceptable for general coding help but did not reliably produce the tool calls the agent workflow required. Model selection is a functional test before it is a sizing exercise.
  4. Sizing needs a real sizer. GPU type and count, KV budget, TP/PP layout, NCCL settings, and container arguments have to be chosen together. NAI's automatic resource calculation covers validated combinations; beyond that, the review recommends NVIDIA's validated configurations and the NAI Sizer.
  5. Design observability and attribution early. Token volume was easy to count. Per-user, team, and model attribution, queue depth, TTFT, TPOT, and showback took longer. The first TaaS report still could not attribute most of its workload.
  6. Multi-tenancy is engineering work. Open items include GPU-memory wiping between tenants, KServe tenant isolation, node re-imaging, model approval, and scoped tokens. These are exactly the problems Astra's projects, resource groups, and fabric isolation are built to solve.

Scaling, ownership, and failure modes

Autoscaling must react before users see a queue, but inference capacity can take tens of seconds or minutes to become usable.

A controller that observes only GPU utilization is late and sometimes wrong: decode can be bandwidth-bound while utilization looks moderate, and a queue can rise while new replicas are still loading. Use a small set of leading and confirming signals, and require a model-level readiness gate before routing traffic.

Failure modes worth designing before launch

HBM OOM during long-context prefill

Infra implication: enforce per-request context and per-replica live-token limits at admission; monitor KV allocation, not only request count.

NCCL or collective timeout

Infra implication: a tensor-parallel replica is one synchronous failure domain; capture rank-level timing and drain the entire replica when one participant degrades.

Tensor-parallel straggler

Infra implication: a single slow GPU, NUMA path, or link stretches every collective; topology-aware placement and per-rank telemetry are required.

Noisy neighbor on the shared fabric

Infra implication: collective and KV-transfer traffic need measurable capacity, isolation, and maintenance coordination with other east-west workloads.

etcd quorum loss

Infra implication: existing workers may continue serving, but desired-state changes and rollouts can freeze; keep payloads out of etcd and test control-plane recovery separately.

Thundering-herd cold start

Infra implication: a deploy or node loss can make many replicas read the same hundreds of gigabytes from one Files share at once; use warm capacity, staged rollout waves, optional LocalModelCache, and measured Files throughput limits.

Host RAM exhaustion from KV offload

Infra implication: the /dev/shm KV tier counts against pod memory; size nodes and pod limits for ≥1.2× GPU memory per GPU, or the offload feature becomes an OOM source.

No free GPU behind the autoscaler

Infra implication: an NKP node-pool scale-up stalls if COCI has no compatible free GPU node; capacity reservations and tenant GPU quotas belong in Astra resource-group planning, not in the autoscaler.

Partial model hydration

Infra implication: never advertise readiness after the container starts; require digest verification, complete HBM load, distributed-group formation, and an inference health check.

Node drain crosses the SLO margin

Infra implication: maintenance capacity is part of steady-state sizing. A replica that spans nodes may disappear as a unit when one node drains.

The operational test is not “Can Kubernetes restart it?” It is “Can the fleet replace this replica, move its bytes, reform its communication group, and absorb traffic without violating the user-facing SLO?”

Artifacts: what training leaves behind

A trained model is not one file. A typical release directory includes architecture and generation configuration, tokenizer assets, documentation, and weight shards. A simplified layout looks like this:

model-v2/
├── config.json # architecture and dimensions
├── generation_config.json # decoding defaults
├── model-00001-of-000xx.safetensors
├── model.safetensors.index.json # shard map
├── tokenizer.json / tokenizer_config.json
├── special_tokens_map.json
└── README.md # model card and usage notes

Training checkpoints are larger still. Besides one copy of the weights, Adam-family optimization commonly maintains first- and second-moment state—roughly two additional model-sized sets—plus scheduler and random-number-generator state. The shorthand is ≈1× weights + ≈2× optimizer state, before format and precision details. Checkpoint storage can therefore dwarf the final serving artifact.

LoRA adapters take the opposite approach: keep a frozen base model and store small learned matrices per task. The adapter is cheap to copy and promote, but it is meaningful only alongside the exact compatible base model.

Serving then creates its own artifacts. Chat history is application state. Prefix-cache snapshots or reusable KV blocks are performance state. Logs, traces, evaluation outputs, and safety records are operational state. “Stateless inference” usually means the worker can be replaced—not that the surrounding system has no state.

The clean promotion pattern is to keep each model build immutable in Objects, import each approved version into its own Files volume, and move a small mutable pointer in the control plane. Promotion becomes a metadata flip from one versioned artifact to another; rollback is the reverse flip. Workers resolve the pointer, mount the referenced volume, load it, pass health checks, and only then take traffic. Never overwrite a model volume that a live endpoint may still be reading.

Files vs Objects: the one rule

Nutanix Files

SMB / NFS · mounted hierarchy · RWX PVC

Files supports folders, in-place edits, byte-range locking, and many readers or writers sharing a POSIX mount. That is exactly what a fleet of vLLM pods needs to read the same model, which is why NAI puts live weights here. NFS over RDMA and the AI Performance Profile make it the fast path.

Nutanix Objects

S3 API · buckets and keys

Objects fits write-once/read-many blobs addressed over HTTPS at data-lake scale. Versioning, lifecycle policy, and replication make it the durable registry for imports, corpora, checkpoints, and archives, while application logic owns concurrency.

If your app speaks S3, it wants Objects. If pods, people, or tools need a shared mounted filesystem—including every NAI replica reading its weights—it wants Files.
Durable imports in Objects · live weights on Files · spilled KV in host RAM · hot state in HBM · pointers in etcd

Capacity-planning checklist

A defensible deployment plan can be reviewed as eight linked calculations. If one input is unknown, mark it as a measurement task rather than filling the gap with a vendor peak number.

  1. Choose the exact model build. Record architecture, total and active parameters, precision, context limit, attention design, license, weight format, and immutable artifact digest. “405B” is not enough if one build is BF16 and another FP8.
  2. Compute the resident weight footprint. Multiply parameters by bytes per parameter, then add measured runtime reserve for graph state, kernels, temporary buffers, and fragmentation. Round to a supported GPU topology—not merely the mathematical minimum. Start from NAI's validated model–GPU matrix and automatic resource calculation where the combination is listed.
  3. Budget KV cache from context × concurrency. Calculate bytes per token from the architecture, then multiply by the maximum admitted live tokens per replica. State context limits and the scheduling policy that enforces them.
  4. Select GPU and node count. Fit weights + KV + reserve into usable HBM. Prefer the fewest high-bandwidth domains that meet latency; record the spare capacity required for maintenance and failover. Check both memory capacity and the bandwidth-derived decode ceiling, and note whether the SKU has NVLink.
  5. Validate the fabric. Map tensor, pipeline, expert, and KV-transfer traffic onto actual links. Benchmark the intended topology under contention, and identify every synchronous failure domain.
  6. Size storage and the cold path. Budget durable capacity for weights, checkpoints, adapters, snapshots, and retention copies. Divide rollout bytes by required rollout time to derive aggregate Files read throughput; include concurrent loads. Budget Objects for the durable copy of every retained version, and host RAM for KV offload if enabled.
  7. Reserve power and cooling. Use node-level maximum envelopes plus switching, storage, and facility overhead. Check rack density, power feeds, cooling, and maintenance capacity before treating GPU inventory as deployable.
  8. Set the warm-pool and rollout policy. Compare demand growth and failure-recovery objectives with measured hydrate-and-initialize time. Pre-stage enough ready capacity to cover that gap, then canary, health-gate, and roll forward in bounded waves. Decide which endpoints stay warm and which may hibernate, and confirm the free GPU nodes in COCI that a scale-up would rely on.

The final unit of capacity is not a GPU. It is a healthy replica, loaded with the right artifact, inside a tested failure domain, with enough HBM and fabric headroom to meet the SLO.

Putting it together: one operating model

Follow one request from a coding agent. It reaches the NAI Agent Gateway, where Envoy checks the API key and quota, and the llm-d endpoint picker chooses the replica most likely to hold the conversation's prefix in its KV cache. KServe runs that replica as a vLLM pod on an NKP GPU node pool, inside an AHV VM with a passed-through GPU, on a compute-only node managed by COCI. Prefill builds KV state; decode streams tokens back through the gateway. Today both phases run in one replica; the target design splits them into separately scaled pools. The weights that replica reads were imported once from Objects (or Hugging Face or NGC) into a Files RWX volume and loaded into HBM when the endpoint started. Cold KV blocks spill to host RAM. Astra brought the GPU node into existence, and Prism Central shows it in the fleet.

Warm endpoint instances keep sudden demand off the cold-start path, and hibernation releases GPUs from endpoints that can tolerate a resume delay. AHV-hosted ancillary services and NKP-managed inference pools share the same Nutanix Unified Storage and observability foundation, while policy decides whether eligible overflow stays on-premises or runs on NAI in a public cloud.

Inference engineering is infrastructure engineering

Choosing a model is choosing the physical shape of the service.

parameter count → GPU count → node count → NVLink domains → inter-node fabric → power, cooling & floor space
≤≈20.4 kW

Maximum whole-system IT load across two occupied DGX H100-class nodes; cooling/PUE is additional.

≈1 TB

Kimi K2 FP8 weight data read from Files into HBM for every replica load.

≈512 GB

KV cache for eight ≈128K-token Llama 405B sessions at the ≈500 KB/token planning value.

That is the core argument. Cold start is a storage and network throughput problem. Expert parallelism is a fabric problem. Long context multiplied by concurrency is an HBM capacity problem. Replica density is a power, cooling, and scheduling problem. Multi-tenancy is a fabric-isolation and control-plane problem. The runtime exposes these pressures; infrastructure determines whether the service survives them.

That is also why Nutanix's AI strategy is layered the way it is. NAI alone cannot fix a missing NVLink domain, a saturated Files share, or a GPU node that was never imaged. Astra, COCI, AHV, NKP, Flow, Files, and Objects exist so that when NAI asks for "one more replica of this model," the answer is a healthy endpoint rather than a ticket.

Small glossary

Prefill
Parallel processing of the input prompt that builds initial attention state.
Decode
The serial loop that generates one token at a time.
TTFT
Time to first token: queueing plus prefill latency as the user experiences it.
TPS / ITL
Tokens per second, or inter-token latency, during decode.
Roofline model
A performance model that relates arithmetic intensity to the ceilings imposed by memory bandwidth and peak compute.
Serving framework
The service layer that queues, batches, schedules, and executes model requests on accelerators.
KV cache
Stored key/value projections of prior tokens, reused by later decode steps.
Quantization
Representing weights or activations with fewer bits to reduce memory and traffic.
Tensor parallelism
Splitting a layer’s tensor operations across tightly connected accelerators.
MoE
Mixture-of-Experts: sparse layers that route each token to a subset of expert MLPs.
Speculative decoding
Drafting tokens with a small model and verifying them in parallel with a larger one.
Cold start
The path from an unavailable replica to one with initialized weights ready in HBM.
LoRA
Small task-specific low-rank adapter weights applied to a frozen base model.
SafeTensors
A tensor serialization format commonly used for sharded model weights.
Disaggregation
Running prefill and decode on separately sized worker pools.
Warm pool
Ready, already-loaded inference capacity held to absorb demand without waiting for a full model cold start.
SM
Streaming multiprocessor: the GPU execution unit that contains CUDA and Tensor Cores.
HBM
High-bandwidth memory attached to the accelerator; the capacity pool that must hold weights, caches, and runtime overhead.
GQA / MLA
Attention designs that reduce KV-cache size by storing fewer or compressed key/value channels.
Expert parallelism
Distributing MoE experts across accelerators; token routing then becomes a fabric operation.
Pipeline parallelism
Assigning consecutive model-layer stages to different accelerators and passing activations between them.
Data parallelism
Running complete model replicas that independently serve different requests.
Collective
A coordinated multi-rank communication operation such as all-reduce or all-to-all.
Live tokens
The prompt and generated tokens currently occupying KV-cache capacity across admitted sequences.
Ridge point
The roofline balance where the bandwidth slope meets the compute ceiling.
NVLink domain
The set of GPUs joined by NVIDIA’s high-bandwidth accelerator interconnect, typically inside one server.
etcd
A consistent control-plane key-value store for small cluster state and pointers—not blobs.
TPOT
Time per output token; NAI's name for inter-token latency during decode.
NAI
Nutanix Enterprise AI: the Kubernetes-native platform that deploys, governs, and serves model endpoints through KServe, vLLM, and NVIDIA NIM.
Agent Gateway
NAI's Envoy-based front door for local endpoints, external providers, and MCP servers: auth, routing, rate limits, and telemetry.
EPP
Endpoint picker from the Gateway API Inference Extension; in NAI, the llm-d scheduler that picks replicas by KV-cache prefix match and load.
NKP
Nutanix Kubernetes Platform: management and workload clusters, GPU node pools, and the NVIDIA GPU Operator.
Project Astra
Nutanix's AI Factory program that turns GPU servers into tenant-aware GPU, Kubernetes, and inference services.
COCI
Centralized Operations for Cluster Infrastructure: a lightweight control plane for up to ≈128 compute-only GPU nodes, with no HCI data path.
CCVS
Cross-Cluster Volume Storage: exports VM boot volumes over iSCSI from an infrastructure cluster to GPU nodes.
Foundation Central / Nico / NIM
Astra's hardware path: imaging and lifecycle, provisioning via BMC/Redfish and health tests, and infrastructure orchestration (NIM here is Nutanix's infrastructure manager, not NVIDIA NIM).
NVIDIA NIM
NVIDIA Inference Microservices: prebuilt, optimized model-serving containers that NAI can deploy as endpoints.
KServe / LLMInferenceService
The Kubernetes serving layer under NAI; LLMInferenceService with LeaderWorkerSet enables multi-node serving.
RWX PVC
A ReadWriteMany Kubernetes volume; in NAI, one per model on a Nutanix Files share, mounted by every replica.
NFS over RDMA / GDS
Faster storage paths: NFS carried over RDMA NICs, and GPUDirect Storage reading straight into GPU memory.
MIG / vGPU
Ways to share one physical GPU: hardware partitions with isolated memory, or hypervisor-level virtual GPUs.
SR-IOV
A NIC exposing hardware virtual functions directly to VMs, bypassing the AHV virtual switch for RDMA traffic.
Hibernation
An NAI endpoint state that releases GPUs without deleting the endpoint; resuming is a cold start.
