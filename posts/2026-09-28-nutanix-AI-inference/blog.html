What inference is

Inference is what happens every time someone uses a trained AI model: a request goes in, and the model sends back an answer.

An AI model's life has two stages. In training, the model learns. Billions of numbers inside it, called parameters or weights, are adjusted over and over until its outputs are good. Training is one long job that runs for days or weeks, and what matters is how much data it gets through. In inference, the learning is over. The weights are frozen, and the model is put to work answering requests as they arrive. Every chat reply, code completion, and coding-agent step is an inference request.

TrainingInference
The weightsChange on every stepStay fixed
Runs asA long batch jobAn always-on service
Success meansGetting through the data in reasonable timeFast answers for someone who is waiting, at a sustainable cost
HappensOnce per model versionOn every request, all day

For a large language model (LLM), answering a request means predicting the next token (a word or piece of a word), appending it to the text, and repeating until the answer is complete. That loop, and the hardware it runs on, is what the rest of this post measures.

A request passes through several layers on its way to a GPU and back:

application            chat UI, IDE agent, RAG pipeline
  → API gateway        authentication, quotas, routing
  → serving framework  vLLM or SGLang: batches requests, manages GPU memory
  → model runtime      PyTorch and GPU kernels: runs the model's math
  → GPU hardware       memory, bandwidth, and compute

The serving-framework layer is where our team will operate the service, but any layer beneath it can set the speed limit. A congested gateway, a serving framework that has run out of GPU memory, and a GPU without enough memory bandwidth all look the same to the user: a slow answer. On Nutanix, the gateway is the NAI Agent Gateway, the serving layer is KServe running vLLM or NVIDIA NIM containers, and those containers run on NKP with GPUs attached through AHV. Where Nutanix fits covers each piece.

Why this matters

Our team is about to operate LLM inference as a service, not just call it. That changes the questions we have to answer.

"Which model is best?" becomes "How many GPUs does this model need, how many nodes does that span, how long does a replica take to come up, and what fails first when a thousand coding agents hit it at once?"

The central claim of this post is simple: choosing a model is choosing the physical shape of the service. Parameter count determines GPU count; GPU count determines node count; node count determines whether the interconnect, the storage path, and the power budget sit on the critical path.

We'll get there in three steps:

  1. Run GPT-2 on a laptop, where every inference concept fits in about 140 lines of Python.
  2. Scale the same concepts to today's open-weight models and do the memory math.
  3. Map each resulting pressure onto the Nutanix stack that turns GPU servers into governed inference endpoints.

All numbers below are approximate planning figures tied to stated assumptions. They are not benchmarks. Production decisions still need measurements from the exact model, precision, serving framework, GPU, and request mix.

Start small: GPT-2 on a laptop

The core problems of large-scale inference already exist in a 124M-parameter model. They are just too small to hurt.

The companion script, code/gpt2-inference.py, runs GPT-2 with no serving framework: a hand-written byte-pair-encoding (BPE) tokenizer, an explicit transformer forward pass, top-p sampling, and a generation loop that reports its own timing.

pip install torch safetensors
python code/gpt2-inference.py   # first run downloads ≈550 MB into ./gpt2-cache

Type a prompt and the script streams a 30-token continuation, then prints the two numbers this whole post revolves around: [TTFT … ms · decode … tokens/s].

Read the script with this map in mind, because every step reappears later as an infrastructure decision:

Script stepOn a laptopAt production scale
download()Fetches the ≈550 MB FP32 checkpoint plus small config and tokenizer files.Importing a model into Nutanix Enterprise AI (NAI): hundreds of GB to ≈1 TB per model, read again by every new replica.
Tokenizer.encodeTurns text into token IDs using the model's own vocabulary and merge files.Request ingress. Tokenizer files are version-locked to the weights; a mismatch silently corrupts output.
First forward(ids)Processes the whole prompt at once. This is prefill.Compute-bound. Sets time to first token (TTFT).
generate() loopOne token per iteration, appended and fed back. This is decode.Memory-bandwidth-bound. Sets tokens per second.
sample_top_pTemperature and nucleus sampling over 50,257 logits.Cheap, but it runs on every step of a serial loop, so it sits on the latency path.
print(..., flush=True)Streams each token to the terminal.Egress through the NAI Agent Gateway as an OpenAI-compatible stream.

The script deliberately omits the most important production optimization: it has no KV cache. Every decode step re-runs attention over the entire sequence. A production engine such as vLLM stores each layer's attention keys and values (the "KV cache") once and processes only the newest token. That trade saves recomputation and spends GPU memory instead. It also means the script's "decode" rate falls as the sequence grows, while a cached engine's stays roughly flat. Most of the rest of this post is about paying that memory bill.

It's worth doing the arithmetic for GPT-2 once:

  • Weights: 124M parameters × 4 bytes (FP32) ≈ 500 MB. Fits in laptop RAM with room to spare.
  • KV cache per token: 2 (keys and values) × 12 layers × 12 heads × 64 dims × 4 bytes ≈ 72 KB/token, or ≈72 MB for a full 1,024-token context.

Hold on to that ≈72 KB/token figure. Kimi K2, a trillion-parameter model later in this post, stores about the same amount per token (≈70 KB, and that's in BF16, half GPT-2's FP32 width per value); Llama 3.1 405B stores about seven times as much. Either way, the per-token figure is not what explodes. Three things around it do:

  • Context length: 128K tokens instead of 1K.
  • Concurrency: thousands of live sessions instead of one.
  • Weights: they no longer fit on one device.

Those three are why inference becomes an infrastructure problem.

Two phases, two bottlenecks

Every generation request has two phases that stress different hardware:

  • Prefill processes the prompt largely in parallel to build attention state. It is dense matrix work and is usually compute-bound.
  • Decode emits one token per forward pass, appends it, and repeats. It is sequential, rereads the weights every step, and is usually memory-bandwidth-bound.

They show up as different user-facing metrics. TTFT captures queueing plus prefill. Time per output token (TPOT), also called inter-token latency, describes the decode stream. NAI endpoint metrics report both, along with output tokens per second and request latency, backed by Prometheus and exportable over OpenTelemetry. That makes per-phase service-level objectives (SLOs) something we can actually measure and enforce.

A worked example shows why the distinction matters. Take an interactive request with a ≈2,000-token prompt, a ≈500-token answer, ≈300 ms of prefill, and ≈50 tokens/s decode:

StageTimeWhat moves it
Ingress≈40 msGateway policy, TLS, network placement
Queue≈110 msReplica count, admission control, warm capacity
Prefill≈300 msCompute throughput, prompt length
Decode≈10,000 msMemory bandwidth, model size and precision, batching
Egress≈50 msStreaming, client network
Total≈10.5 s

Decode is ≈97% of model time. Making prefill faster improves the first visible token (≈500 ms here) but barely changes when the answer finishes. That is why we write two budgets, a first-token budget and a completion budget, and track p50 and p99 for each. Averages hide queueing; the p99 tail is where users feel it.

The average tells you the machine is healthy. The tail tells you whether users agree.

The two numbers that describe a GPU

For inference, a GPU is described by two numbers: how many bytes its memory holds, and how fast it can read them.

Capacity decides whether the model and its KV cache fit. Bandwidth decides how fast decode runs once they do. At batch size 1, each decode step must read every active weight once, which gives a hard ceiling no kernel optimization can beat:

decode ceiling (tokens/s per stream) ≤ aggregate memory bandwidth ÷ active-weight bytes per token
ScenarioMathCeiling
Llama 3.1 405B (dense), FP8, 8×H100≈26.8 TB/s ÷ ≈405 GB≈66 tokens/s
70B dense, FP8, 1× RTX PRO 6000≈1.6 TB/s ÷ ≈70 GB≈23 tokens/s
gpt-oss-120b (MoE), MXFP4, 1× RTX PRO 6000≈1.6 TB/s ÷ ≈5 GB active≈320 tokens/s

For gpt-oss-120b, "active" means the four routed experts per layer in MXFP4 (≈1.9 GB) plus the attention and output layers, which every token reads and which ship in BF16 (≈3 GB). All three ceilings ignore KV-cache reads, which add bytes to every step as the context grows.

The first row explains why ≈50 tokens/s in the latency budget is realistic rather than pessimistic. The second shows that a model can fit on a GPU and still be too slow on it. The third shows what Mixture-of-Experts (MoE) models do: a router sends each token to only a few expert sub-networks, so far fewer bytes are read per token. That shifts the pressure from bandwidth to capacity, because all experts still have to stay resident in memory.

Batching is the other lever. Many streams share one read of the weights per step, so aggregate throughput rises with batch size until KV-cache reads or compute catch up. The memory left over after weights sets the maximum batch.

The GPUs NAI 2.8 supports span a wide range on both axes:

The last column matters as soon as a model spans more than one card. Without NVLink, every tensor-parallel all-reduce crosses PCIe. We'll see that effect in production in the field notes below.

Do the math: what today's open models require

Model selection is capacity planning. Four formulas get you most of the way.

weight memory   = parameters × bytes per parameter        (BF16 = 2, FP8 = 1, INT4 ≈ 0.5)
KV per token    ≈ 2 × layers × kv_heads × head_dim × bytes
GPU count       = ceil[(weights + live KV) ÷ usable memory per GPU]
node count      = ceil(GPUs ÷ 8 per node)

For the table below, "usable" means 90% of an 80 GB H100 (72 GB), leaving headroom for runtime buffers and allocator fragmentation. All weights are FP8 and fully GPU-resident for low-latency serving.

ModelParams (total / active)FP8 weightsH100s (capacity / provisioned)Nodes
gpt-oss-120b≈117B / ≈5.1B (MoE)≈117 GB2 / 21
Qwen3-235B-A22B≈235B / ≈22B (MoE)≈235 GB4 / 41
Llama 3.1 405B≈405B / ≈405B (dense)≈405 GB7 / 81
DeepSeek V3.1≈671B / ≈37B (MoE)≈685 GB10 / 162
Kimi K2≈1T / ≈32B (MoE)≈1.03 TB15 / 162

Each row budgets one 128K-token sequence of KV cache on top of weights. For example, Llama 3.1 405B: (405 GB + ≈64 GB KV) ÷ 72 GB = 6.5, which rounds to 7 by capacity and to the published 8×H100 topology in practice.

The "provisioned" column rounds up to layouts serving frameworks actually run. Tensor parallelism splits attention heads across GPUs, so its degree has to divide the head count (64 or 128 for these models); in practice that means 2, 4, or 8 GPUs inside one NVLink node, which is why Llama's 7 becomes 8. A replica larger than one node adds pipeline or expert parallelism across nodes, and schedulers hand out whole nodes. That is why DeepSeek's 10 becomes 16: two full nodes, not one and a quarter.

gpt-oss-120b ships natively in MXFP4 (≈4.25 bits per expert weight, ≈65 GB on disk) and is designed to fit a single 80 GB GPU. It is shown at FP8 here only to keep the rows comparable.

Two things stand out.

The MoE rule. Kimi K2 computes with ≈32B active parameters per token, but you provision memory for the whole trillion. Offloading experts to host memory or NVMe can cut GPU memory demand, but adds traffic and latency.

The one-to-two-node jump changes the problem. Once a replica spans two nodes, tensor collectives and expert routing leave the NVLink domain, placement consumes rack-level power (a fully populated DGX H100 is rated at ≈10.2 kW maximum), and any failure or drain operation moves a near-terabyte footprint.

The GPU choice changes the answer. Kimi K2's weights plus one 128K session come to ≈1,038 GB. On B300 (≈259 GB usable), that is about 4 GPUs' worth, so a replica fits inside one 8-GPU NVLink domain with roughly another terabyte left for KV cache. On RTX PRO 6000 (≈86 GB usable), it is about 12 GPUs' worth, 16 in practice, across two PCIe-only nodes: feasible on paper, but every collective crosses PCIe and the network.

Choosing a GPU SKU really means choosing how many failure domains a replica spans.

KV cache: the concurrency multiplier

Weights decide whether one replica fits. KV cache decides how many requests that replica can serve at once.

Llama 3.1 405B stores ≈500 KB of KV cache per token in BF16. One full 128K-token session is ≈64 GB. Eight concurrent 128K sessions need ≈512 GB of KV cache, more than the ≈405 GB of weights. Eight H100s offer 640 GB nominal, which cannot hold both. At 90% usable, they leave ≈170 GB after weights: room for just two full-length sessions per replica. The model fits; the workload does not.

Models that use multi-head latent attention (MLA), such as DeepSeek V3.1 and Kimi K2, store a compressed representation instead, at ≈70 KB/token (about GPT-2's figure). Eight 128K sessions then need ≈72 GB. Attention architecture is an infrastructure input, not just a model-quality detail.

In practice, every deployment should state three numbers explicitly: the maximum admitted context, the maximum live tokens per replica, and the memory reserve that cannot be allocated to KV. Without them, a few long-context prompts can stall admission or crash a worker even when request count looks low.

NAI 2.8 ships early versions of two KV features, both Tech Preview:

  • KV-cache-aware routing. The open-source llm-d scheduler, running as the Gateway API Inference Extension's endpoint picker (EPP), tracks which prefixes each vLLM replica holds and routes requests to the best match. Coding agents that resend a long system prompt and tool schema every turn skip most of prefill, which cuts TTFT.
  • KV-cache offload to host RAM. Evictable KV blocks spill to host memory instead of being discarded. It requires at least 1.2× GPU memory per GPU in host RAM: on an 8×H200 node, that is ≈1.35 TB set aside. It improves repeat-prompt TTFT, not decode speed.

Where Nutanix fits

The model server is one process in a layered system. Nutanix contributes everything around it, and each product has a specific job.

The umbrella that packages them into an AI Factory is Project Astra, whose promise is "user intent → ready-to-use GPU or inference service."

GPU servers
  → Foundation Central + NICo     discover, health-check, image
  → NIM (Nutanix Infra Manager)    claim nodes, build clusters
  → AHV + COCI                     GPU VMs on compute-only nodes
  → Prism Central projects         tenancy for GPUs and networks
  → NKP                            Kubernetes workload clusters
  → NAI                            model endpoints

NICo (NVIDIA Infra Controller) is NVIDIA's open-source bare-metal lifecycle manager. It discovers and validates hosts over Redfish, manages host firmware and BlueField DPUs, and monitors hardware health, so new GPU servers arrive as API-managed building blocks rather than hand-built machines. "NIM" here is Nutanix's infrastructure manager, not NVIDIA NIM inference microservices, which appear later inside NAI.

ComponentJob in the inference stack
Nutanix Enterprise AI (NAI)Deploys and governs LLM endpoints. You pick a model from the validated catalog (Hugging Face, NVIDIA NGC/NIM, or manual import); NAI selects the runtime and GPU profile, creates KServe objects and storage, and exposes an OpenAI-compatible endpoint behind the Envoy-based Agent Gateway.
NKP (Nutanix Kubernetes Platform)Runs the Kubernetes clusters that host NAI, with dedicated GPU node pools and the NVIDIA GPU Operator. Its autoscaler can add GPU workers, but only if AHV has compatible free GPUs.
AHVAttaches GPUs to NKP worker VMs: whole-GPU passthrough for large models, MIG inside the guest for isolated fractional GPUs, or vGPU for consolidation.
COCI (Centralized Operations for Cluster Infrastructure)A lightweight control plane for up to ≈128 compute-only GPU nodes, with no HCI storage data path, so GPU capacity and storage capacity scale independently. Each COCI cluster is a failure and maintenance domain.
FlowPer-tenant VPCs and security policy for north–south and Kubernetes traffic. It deliberately stays out of the GPU collective path, which is isolated on its own InfiniBand or RoCE fabric.
FilesThe live model repository. NAI creates one ReadWriteMany (RWX) volume per model, and every replica mounts it at /mnt/models. NFS over RDMA shortens the load path.
ObjectsThe durable, S3-compatible source for model imports (including air-gapped NIM bundles), RAG corpora, datasets, and checkpoints. Bytes arrive and are retained here; replicas don't read from it on every start.
Prism CentralTenancy boundary (projects and resource groups) plus the fleet view: capacity pressure, maintenance state, and the shared blast radius behind an apparently healthy endpoint.

The cold path: Objects → Files → GPU memory

Weight loading is a storage-and-network pipeline before it is a GPU operation. In NAI, bytes are written once into a shared Files volume and read by every replica that starts, so the Files read path is the cold-start path.

cold-start lower bound = model bytes ÷ effective end-to-end load bandwidth

For a ≈400 GB FP8 model at the ≈10 GB/s per-node sequential read cited for Nutanix Unified Storage, the floor is ≈40 seconds, before deserialization, KV allocation, collective-group setup, and health checks. At a more typical ≈5 GB/s effective path, it's ≈80 seconds. Real loads can be much worse: internal troubleshooting logs recorded vLLM taking ≈140 seconds to load ≈40 GB of a 4-bit 70B model on L40S (≈0.3 GB/s), because deserialization, not storage, dominated. Measure the load; don't derive it from a spec sheet.

A container reporting "Running" proves almost nothing. A replica is ready only after its weights are loaded, KV blocks are allocated, its distributed group has formed, and it passes a model-level health check. That gap is why warm endpoint instances matter. NAI supports manual scaling of endpoint instances without downtime, and hibernation to release GPUs from endpoints whose users can tolerate a resume delay. Scale-to-zero is deliberately disabled, because scaling from zero is a full cold start.

A few features are still in progress: multi-node serving is a Tech Preview in NAI 2.8, and prefill/decode disaggregation (separate, independently scaled pools for each phase) is on the roadmap, not generally available. Plan today's endpoints as unified replicas.

Field notes: our own GPU Farm

Nutanix already runs this stack for its own engineers, and the results match the arithmetic above.

Internal IT operates a GPU Farm that serves Token-as-a-Service (TaaS) to Nutanix developers, mostly for coding agents, plus chat, RAG, embeddings, and reranking. A developer requests a key from an internal portal that calls NAI; from then on, the NAI gateway handles authentication, quotas, rate limits, routing, and token accounting.

96 × RTX PRO 6000

Blackwell Server Edition, 8 per node across 12 nodes. 96 GB GDDR7 each, PCIe Gen5, no NVLink.

≈42B tokens / week

Generated tokens in the TaaS report dated September 25, 2026.

619 onboarded users

Up 62% from the previous report, with planning for ≈1,500 and later ≈3,000.

The lessons map directly onto the sections above:

  • Capacity is cheap; interconnect is not. A 96 GB card holds a lot of model, but without NVLink, tensor parallelism across cards pushes every all-reduce over PCIe and hurts inter-token latency for 30B–120B-class models.
  • MoE on one GPU is the sweet spot. The agent platform runs Qwen3.6-35B-A3B on a single RTX PRO 6000: ≈3B active parameters give a high decode ceiling, and a single GPU means no PCIe collective penalty.
  • Benchmark quality isn't agent compatibility. gpt-oss-120b was acceptable for general coding help but didn't reliably produce the tool calls the agent workflow required. Model selection is a functional test before it's a sizing exercise.
  • Design observability early. Counting tokens was easy. Per-user and per-team attribution, queue depth, TTFT, TPOT, and showback took longer.

Figures come from internal GPU Farm, TaaS, and Astra pages as of late September 2026. Internal records differ on whether the inventory is 90 or 96 GPUs; confirm before quoting outside the team.

Takeaways

  • The per-token KV footprint doesn't have to grow with model size. Context length, concurrency, and weights that outgrow one device are the multipliers, and they turn a laptop script into a hardware, storage, and network problem.
  • Prefill sets TTFT and is compute-bound; decode sets completion time and is bandwidth-bound. Budget and measure them separately, at p99.
  • Check both capacity and bandwidth for every model–GPU pair. A model can fit and still be too slow.
  • KV cache, not weights, usually limits concurrency. State admitted context and live-token limits per replica.
  • The GPU SKU decides how many failure domains a replica spans. Staying inside one NVLink domain is worth a lot.
  • Cold start is a load-pipeline problem. On NAI it runs through Files, but deserialization can dominate; measure the whole load and keep warm capacity to cover it.
  • Nutanix's stack is layered for a reason: Astra and COCI make GPUs exist, AHV attaches them, NKP schedules them, NAI turns them into endpoints, Files and Objects hold the bytes, and Prism Central shows the fleet.

Glossary

Training / inference
Adjusting a model's weights until it performs well, versus using those fixed weights to answer requests.
Token
The unit an LLM reads and writes: a word or piece of a word, roughly ¾ of an English word on average.
Serving framework
Software such as vLLM or SGLang that loads a model onto GPUs, batches incoming requests, and streams answers back.
Prefill / decode
The parallel prompt-processing phase and the serial token-generation loop.
TTFT
Time to first token, which is queueing plus prefill as the user experiences it.
TPOT / ITL
Time per output token, or inter-token latency, during decode.
KV cache
Stored attention keys and values for prior tokens, reused by later decode steps.
HBM
High-bandwidth memory attached to a data-center GPU.
MoE
Mixture-of-Experts; each token activates only a subset of the model's expert sub-networks.
MLA / GQA
Attention designs that shrink the KV cache by storing compressed or fewer key/value channels.
NICo
NVIDIA Infra Controller, an open-source service suite for bare-metal discovery, firmware, DPU provisioning, and hardware health.
NVLink
NVIDIA's high-bandwidth GPU-to-GPU interconnect, typically within one server.
EPP
Endpoint picker from the Gateway API Inference Extension; in NAI, the llm-d scheduler.
RWX
ReadWriteMany, a Kubernetes volume that many pods can mount at once.
